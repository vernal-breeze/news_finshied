# 运行时问题与不足点清单

这份文档只做问题梳理，不修改代码。当前基于源码检查和本地校验，先把会影响启动、构建、页面行为的点整理出来，方便后续决定修复优先级。

## 结论先行

当前项目不是“完全可用但有小瑕疵”，而是已经存在几个会直接影响交付的点：

1. 前端构建已经失败。
2. 读者消息功能的前后端数据结构不一致，页面行为会明显异常。
3. 有些接口目前还是占位实现，点了也不会真的完成业务动作。
4. 后端启动对环境变量依赖较强，默认配置下可能直接拦启动。

## 一、会直接影响构建或启动的问题

### 1. 前端 `npm run build` 失败

- 位置：[`frontend/src/utils/tags.ts`](../frontend/src/utils/tags.ts:15)
- 现象：`tsc` 报错 `'> expected'`、`Unterminated regular expression literal` 等。
- 原因：这个文件是 `.ts`，但里面写了 JSX：`<Tag ...>...</Tag>`。
- 影响：前端生产构建会直接中断，当前状态无法正常打包发布。
- 说明：我已经在本地跑过 `npm run build`，错误就卡在这里。

### 2. 后端默认密钥会阻止非调试环境启动

- 位置：[`backend/app/core/config.py`](../backend/app/core/config.py:154-156)
- 现象：当 `DEBUG=false` 且 `SECRET_KEY` 还是默认值时，代码会主动抛出 `RuntimeError`。
- 影响：只要 `.env` 没配好，或者部署时漏了 `SECRET_KEY`，服务就起不来。
- 评价：这个保护本身是合理的，但对首次运行和部署体验比较苛刻，属于高敏感启动门槛。

### 3. `backend/app/main.py` 的直接运行入口有路径风险

- 位置：[`backend/app/main.py`](../backend/app/main.py:181-189)
- 现象：`uvicorn.run("main:app", ...)` 这个写法只在特定运行方式下成立。
- 影响：如果有人直接执行 `python backend/app/main.py`，模块导入路径很容易不对。
- 评价：平时如果都用 `uvicorn app.main:app` 或 `start.sh`，影响会小一些，但这个入口本身还是不稳。

## 二、功能行为不一致或会“看起来能点，实际上没做完”的问题

### 4. 读者消息中心的数据结构和页面预期不一致

- 后端模型：[`backend/app/models/message.py`](../backend/app/models/message.py:4-9)
- 后端接口：[`backend/app/routers/messages.py`](../backend/app/routers/messages.py:11-29)
- 前端页面：[`frontend/src/pages/reader/Messages.tsx`](../frontend/src/pages/reader/Messages.tsx:37-133)

#### 问题点

- 后端 `Message` 模型只有 `id / content / sender / created_at`。
- 但前端消息页在用 `type`、`is_read`、`created_at` 这些字段来渲染状态、图标和未读标记。
- `unread-count` 接口返回的是 `{ count: 0 }`，而前端 `fetchUnreadMessageCount` 期望的是直接拿到一个数字。
- `reply_message` 接口虽然接收了路由参数，但没有接收或保存回复内容。

#### 影响

- 消息列表会出现字段缺失，未读状态和消息类型基本无法正常工作。
- “标记已读”和“回复”按钮目前更像是视觉上的按钮，不是真正完成了消息流转。

#### 结论

这是一个比较核心的业务缺口，因为它直接影响读者端消息中心的可用性。

### 5. 图片上传接口是占位实现

- 位置：[`backend/app/routers/public.py`](../backend/app/routers/public.py:102-104)
- 现象：`upload_image()` 直接返回 `"上传功能暂未实现"`，并且始终给空 URL。
- 影响：只要前端有图片上传、封面图上传或富文本插图流程，这里就会卡住。
- 评价：这是明确的未完成接口，不是小 bug。

### 6. 反馈与审核相关接口里仍有不少假数据/空实现

- 位置示例：
  - [`backend/app/routers/feedback.py`](../backend/app/routers/feedback.py:17-46)
  - [`backend/app/routers/reviews.py`](../backend/app/routers/reviews.py:22-49)
  - [`backend/app/routers/collection.py`](../backend/app/routers/collection.py:11-31)

#### 现象

- 趋势接口直接返回空数组。
- 一些评论、收藏、任务、版本管理接口只返回固定结构，没有真实业务落库。
- 审核流程里有不少地方更偏“演示数据”，不是完整生产逻辑。

#### 影响

- 页面看起来像是功能齐全，但数据不会持续沉淀。
- 一旦进入真实使用场景，统计、追踪和流程闭环会比较弱。

## 三、其他值得提前知道的不足

### 7. 前端构建配置依赖比较重

- 位置：[`frontend/vite.config.ts`](../frontend/vite.config.ts:32-38)
- 现象：打包时把 `antd`、`@ant-design/icons`、`axios` 直接拆成了固定 chunk。
- 影响：这本身不是 bug，但一旦相关依赖版本或导入方式调整，构建链条会比较敏感。

### 8. 当前项目对本地环境依赖较多

- 位置：`start.sh`、`backend/app/core/config.py`、`docker-compose.yml`
- 现象：需要 Python、Node、数据库、环境变量、前端代理一起配合。
- 影响：新环境第一次启动时，最容易遇到的不是业务 bug，而是“启动链条没接上”。

## 四、建议的修复顺序

如果后面要改，我建议按这个顺序来：

1. 先修前端构建失败的 `frontend/src/utils/tags.ts`。
2. 再把读者消息中心的后端字段和前端预期统一。
3. 然后补齐图片上传和其他占位接口。
4. 最后再整理启动配置和入口稳定性。

这样做的好处是，能先把“跑不起来”和“点了没反应”的问题压下去，再处理体验和完整度。
